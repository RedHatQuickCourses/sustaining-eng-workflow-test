#  Verifying vulnerable function calls in compiled code

= Verifying Vulnerable Function Calls in Compiled Code

Once a CVE has been identified and a potential patch is developed, confirming the fix at the source code level is only half the battle. In the context of RHEL Sustaining Engineering, we must verify that the compiled machine code no longer contains the vulnerable logic. This process ensures that the fix was not only applied correctly but also preserved through the compilation and optimization pipeline.

== Understanding the Verification Challenge
When a vulnerability is located within a specific function, simply inspecting the source code is insufficient. Compilers can perform aggressive optimizations—such as inlining, loop unrolling, or dead-code elimination—which may alter the control flow or even remove the vulnerable function entirely, or conversely, create new execution paths.

To verify the compiled binary, we must bridge the gap between the source-level fix and the binary-level reality.

== Workflow: From Patch to Binary Verification
The verification process involves tracing the vulnerable function calls from the source-level logic down to the assembly level within the shared object (`.so`) or executable binary.

=== Step-by-Step: Binary Analysis Procedure

Follow these steps to verify that the vulnerable function call has been remediated in the compiled RPM.

=== 1. Extract the Compiled Artifact
Before analysis, ensure you are working with the binary generated by the patched build (Brew).

[source,bash]
----
# Extract the RPM package to retrieve the binaries
rpm2cpio <package_name>.rpm | cpio -idmv
# Locate the target library or binary
find . -name "libvulnerable.so"
----

=== 2. Locate the Vulnerable Symbol
Use `nm` or `objdump` to inspect the symbol table. This confirms that the vulnerable function exists in the binary and identifies its address.

[source,bash]
----
# List symbols and filter for the vulnerable function
nm -D libvulnerable.so | grep <vulnerable_function_name>
----

=== 3. Disassemble the Control Flow
To verify the fix, we use `objdump` to examine the assembly instructions. We are looking for the removal of dangerous instructions or the addition of boundary checks (e.g., bounds checking before a buffer copy).

[source,bash]
----
# Disassemble the function to view the assembly code
objdump -d -j .text libvulnerable.so | sed -n '/<vulnerable_function_name>:/,/^$/p'
----

*   **What to look for:**
    *   **Inlining:** If the function is inlined, it may not appear as a distinct call. Check if the code previously surrounding the call has changed.
    *   **Boundary Checks:** Look for `cmp` (compare) instructions followed by conditional jumps (`jle`, `jne`) that prevent illegal memory access.
    *   **Safety Primitives:** Verify that functions like `strcpy` have been replaced by their safer counterparts (`strncpy`, `strlcpy`) in the disassembly.

=== 4. Trace Reachability
If the function is large, use `callgraph` or static analysis tools to verify the call path. Ensure that the vulnerable code path is now unreachable or correctly guarded.

[TIP]
====
If `govulncheck` (for Go-based components) was used during the analysis phase, compare its output before and after the patch. It provides a high-level view of whether the vulnerable function remains in the call stack.
====

== Troubleshooting Verification
If the binary still shows evidence of the vulnerability:

1.  **Check Compiler Flags:** Ensure that `_FORTIFY_SOURCE` or stack-protector flags were active during the Brew build.
2.  **Verify Debug Symbols:** If you cannot see function names, ensure the `debuginfo` package for the RPM is installed.
3.  **Cross-Reference with `dist-git`:** Verify that the `rhpkg` patch was correctly applied to the sources before the build triggered. If the patch did not apply cleanly, the binary will not reflect the fix.

== Summary Checklist for QE
* [ ] Binary extracted from the patched Brew build.
* [ ] Symbol verification confirms the patched code is present.
* [ ] Disassembly validates that security bounds or logic gates are active.
* [ ] No regression detected in adjacent function calls.
* [ ] Results documented in the Jira ticket for the Errata sign-off.
