Building RPMs within the Brew environment

Building RPMs within the Brew Environment

In the Red Hat ecosystem, Brew (the internal implementation of the Koji build system) serves as the centralized infrastructure for compiling source code into installable RPM packages and container images. For security engineers and developers, understanding how to interact with Brew is critical for moving a vulnerability fix from a patched source code state to a distributable update.

The Role of Brew in CVE Resolution

When a patch is applied to a dist-git repository, the source code must be compiled into binary RPMs. Brew ensures that these binaries are created in a controlled, reproducible environment that matches the target distribution release (e.g., RHEL 8, RHEL 9).

For CVE remediation, Brew provides specific functionality to handle security updates, particularly those under embargo:

  • Standard Builds: Used for routine updates where the package is immediately ready for distribution via the Content Delivery Network (CDN).

  • Scratch Builds: Temporary builds used for validation. They do not persist in the repository and are not intended for production release.

  • Nocompose Builds: Specialized builds used for embargoed CVEs. These allow engineers to generate signed RPMs without triggering the automated repository composition (nightly composes), ensuring the fix remains private until the public disclosure date.

Hands-on Activity: Building and Verifying RPMs

This activity covers the process of verifying your patch via a scratch build and triggering an official build for a CVE fix.

Prerequisites

  • An active rhpkg configuration authenticated with your credentials.

  • A patched dist-git repository.

Step 1: Performing a Scratch Build

Before committing your changes to the official branch, perform a scratch build to verify that your code compiles across all required architectures. This prevents "broken builds" in the main line.

# Build the source RPM and submit to Brew for scratch analysis
rhpkg scratch-build --srpm

# Alternatively, specify architectures for broader validation
rhpkg scratch-build --arches x86_64,aarch64,ppc64le,s390x

Step 2: Triggering an Official Build

Once your changes are committed and pushed to the relevant branch, you must trigger an official build. If you are handling an embargoed CVE, you must use a nocompose target to maintain confidentiality.

# Trigger a standard official build
rhpkg build

# Trigger an official build using a nocompose target for embargoed CVEs
# Replace <target-release> with your specific RHEL version/target
rhpkg build --target <target-release>-nocompose

Troubleshooting and Best Practices

  • Build Failures: If a build fails in Brew, examine the build logs provided in the Brew web interface. Common issues include missing build dependencies (BuildRequires in the spec file) or architecture-specific compilation errors.

  • Tracking NVR: Always record the NVR (Name-Version-Release) generated by Brew. You will need this NVR to link the build to an Errata Tool advisory in the subsequent phase of the workflow.

  • Dependency Management: If your CVE fix introduces new dependencies, ensure these are available in the buildroot. Attempting to build against unavailable dependencies will result in a build failure.

  • Architecture Parity: Always build for all supported architectures unless explicitly instructed otherwise. A fix that compiles on x86_64 but fails on aarch64 will prevent the update from shipping for the entire platform.
